# Design decisions

These decisions describe the product at a level appropriate for a public portfolio. They intentionally omit proprietary implementation details.

| Decision                                                                           | Rationale                                                                                                                                      | Alternative considered                                                                                            |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| One CommonJS Node.js codebase for Windows and Linux                                | Keeps behavior and fixes aligned across local and hosted environments. Platform-specific tool resolution isolates executable differences.      | Separate platform implementations would duplicate runtime and deployment logic.                                   |
| Use a headless browser for session setup, then WebSocket and REST for runtime work | Separates browser-driven authentication from the long-running event and control paths. The browser does not need to remain the room transport. | Keeping browser automation open for all live work would couple runtime operation to a browser page.               |
| Scope player and queue state per room                                              | Prevents playback actions in one room from changing another room's queue.                                                                      | A single shared player would not support independent rooms.                                                       |
| Keep client configuration in SQLite and reconcile it periodically                  | Provides durable local state for a single-host service and allows panel changes to converge into runtime room connections.                     | An in-memory-only registry would be lost on restart; a separate network database adds operational infrastructure. |
| Separate administration from room command handling                                 | Provides an operator-facing control surface for client lifecycle and language settings without mixing those workflows into room chat.          | Chat-only administration would make operational controls dependent on room access.                                |
| Stream converted audio over HTTP and publish it through an HTTPS proxy             | Keeps audio delivery distinct from chat transport and supports a public radio listener URL.                                                    | Delivering the audio itself over the chat connection would couple unrelated traffic and lifecycles.               |
| Keep AI optional and configurable per room                                         | Music remains usable without an AI account, provider availability, or AI settings. Provider fallback can be configured independently.          | Making AI mandatory would place a third-party service in the core music path.                                     |
| Keep metrics and the admin panel local by default                                  | Limits exposure of operational controls and diagnostics; hosted operators can use a local access tunnel when needed.                           | Binding every interface publicly would increase the operational exposure surface.                                 |
